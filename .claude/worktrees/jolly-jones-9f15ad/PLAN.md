# Music Hackspace Lisbon 2026 — Algoriddim Track Plan

## Context

Music Hackspace Hackathon Lisbon, **16–17 May 2026** at Unicorn Factory Lisboa. We are entering the **Algoriddim challenge** track with a 6-person team. Goal: win the Algoriddim prize **and** be in contention for a TouchDesigner license by also nailing the visual category.

**Core thesis:** **AI builds the visual instrument.** Most teams will spend the weekend hand-crafting a single cool visual. We build the *tooling layer* that turns any visual scene into an opinionated, playable instrument — automatically — so a DJ can perform visuals without thinking and without setup work.

The DJ gets a small, well-designed control surface (knobs, toggles, pads) that is **generated by AI** from whatever visual scene is loaded. Swap the scene → new controller. Plug in a different physical controller → new mapping. The expressive layer adapts; the DJ doesn't.

**Differentiator:** every other team is building visuals. We're building the *meta-layer* — the thing that makes any visuals playable. That's the unique angle in this hackathon, and a real product direction beyond the weekend.

## System model — three layers

The system separates cleanly into three design surfaces. Each layer has its own owner, its own contract with the next layer, and can evolve independently.

```
┌─────────────────────────────────────────────────────────────────────┐
│ Layer A — Algoriddim signals (raw inputs)                           │
│   stems audio (drums/bass/vocals/melody) • BPM • beat grid •        │
│   key • per-deck EQ/fader/FX • crossfader • cue/loop state • ...    │
└────────────────────────────┬────────────────────────────────────────┘
                             │  TD ↔ Algoriddim integration (built-in, no custom code)
                             ▼
┌─────────────────────────────────────────────────────────────────────┐
│ Layer B — Generic visual modules in TouchDesigner                   │
│   reusable visuals that take Layer A inputs (kick, snare, bass      │
│   level, BPM, ...) and expose tweakable PARAMETERS                  │
│   (intensity, color, scale, density, decay, ...)                    │
└────────────────────────────┬────────────────────────────────────────┘
                             │  Parameter API (named, typed, ranged)
                             ▼
┌─────────────────────────────────────────────────────────────────────┐
│ Layer C — Visual controller (AI-GENERATED)                          │
│   AI reads Layer B's parameter catalog and emits an opinionated     │
│   control surface spec: which params to expose, grouped how, with   │
│   what macros and curves. A renderer turns the spec into a live UI  │
│   (v1) or maps it to a physical MIDI controller (v2).               │
└─────────────────────────────────────────────────────────────────────┘
```

The split is the point: **the music drives the visuals (A→B), and AI auto-designs the control surface (C) for whatever scene is loaded.** Layers B and C are decoupled — Bernardo and Calin can keep changing visuals, the AI re-generates the controller in seconds, the DJ never has to relearn.

## Scope: v1 / v2 / v3

**v1 — what we ship in 2 days (AI tooling is in the critical path):**
- **Foundation (Calin's first task):** a minimal TD prototype that pulls Algoriddim signals directly via the TD-Algoriddim integration and drives a single working visual. Everything else builds on this.
- Layer B: a small library of generic visual modules in TouchDesigner, each exposing a machine-readable parameter catalog (`name`, `type`, `range`, `semantic tag`). Multiple **scenes** (compositions of modules) are pre-built for the demo.
- **Layer C is AI-generated**: an LLM reads the active scene's parameter catalog and emits a controller spec (JSON) — which params to expose, grouped how, with what macros and curves. A renderer turns that spec into a live software UI (tablet-friendly) that writes back to Layer B via OSC.
- **Scene-swap pipeline**: a button press changes the active TD scene → TD pushes the new catalog → AI regenerates the ControllerSpec (~2s, with cached fallback) → renderer rebuilds the UI. Two visible changes (visuals + controls) on one button.
- The killer onstage moment: **swap the visual scene mid-demo → AI regenerates the controller in seconds → Alex keeps playing**
- Alex DJs *and* plays the AI-generated controller live — single-performer, directly embodying the "no thinking" thesis

**v2 — bring-your-own physical controller (stretch on Sunday, headline of the pitch):**
- Plug in any MIDI controller; AI reads its input topology + the current Layer B parameter catalog and generates a mapping
- A small visual overlay shows what each physical control is doing right now
- Guille owns the physical integration; Dan owns the AI mapping prompt

**v3 — Autopilot mode:**
- Same AI-generated controller, but now AI *plays* it — turns the knobs, hits the pads, runs the macros — driven by the music signals from Layer A (BPM, stems, energy, key, structure)
- DJ can hand off to autopilot, take it back, or run hybrid (some controls automated, some manual)
- The DJ-↔-AI handoff itself becomes an expressive performance move

**v4 — Background agent with full TD control (auto-everything):**
- A background AI agent talks to TouchDesigner via MCP — not just turning knobs on the existing controller, but reconfiguring the scene itself (loading modules, rewiring inputs, tweaking compositions)
- Effectively: an autonomous VJ that watches the music and reshapes both the visuals and the controller in response
- The pinnacle of the "no thinking" thesis

**Also deferred:** closed loop (visuals → OSC back to djay).

## Architecture

```
djay Pro ──(TD-Algoriddim integration)──→ TouchDesigner (Calin)
                                          Layer B: generic visual modules
                                          + parameter catalog (JSON, exported)
                                                  ▲
                                                  │  parameter writes (OSC)
                                                  │
                                  Layer C — AI-generated controller (Dan + Guille)
                                                  ▲
                              ┌───────────────────┴────────────────────┐
                              │  1. Param catalog ──→ LLM ──→ UI spec   │
                              │  2. Spec ──→ Renderer ──→ live UI       │
                              │  3. User input ──→ OSC ──→ Layer B      │
                              └─────────────────────────────────────────┘
                                                  ▲
                                                  │  (v2) physical MIDI input → AI mapping
                                                  │  (v3) autopilot — AI drives the controls
```

### Layer A — signals (Calin + Guille)

Two sources, both fed into TD as CHOPs/DATs that Layer B modules consume:

1. **TD ↔ Algoriddim integration (Calin)** — built-in, no custom service. Surfaces BPM, beat grid, stems audio, key, deck/EQ/fader/FX state.
2. **Audio signal extraction (Guille)** — extracts richer features from the stem audio than the integration alone exposes: per-stem RMS envelopes, onset detection, transients, spectral centroid / brightness, harmonic content. Can run as TD CHOPs (Audio Analysis CHOP family) or as an external tool sending OSC into TD — Guille's choice based on what gives him faster iteration.

Together these form the **signal bus** Layer B modules subscribe to. Guille's extraction work directly enriches what visuals can react to.

### Scenes and scene-swap

A **scene** is a configured composition of Layer B modules — which are active, what signals they're wired to, what parameters they expose. Calin authors 2–3 scenes for the demo as **separate COMPs inside a single TD project**, toggled live.

Scene-swap flow:
1. Trigger → activate the new COMP; deactivate the previous one (**trigger mechanism TBD** — likely a UI button or MIDI cue; could also be Calin operating sideboard, or auto on Algoriddim cue — decide during rehearsal)
2. TD exports the updated `parameter-catalog.json` (built from the active COMP's exposed params) and pushes it to the renderer (OSC + file watch, or WebSocket)
3. Renderer sends catalog to AI generator → receives new ControllerSpec
4. Renderer rebuilds the UI from the spec
5. Total latency target ≤3s; during regen show a "regenerating…" pulse
6. **Fallback**: pre-generate specs for all demo scenes Saturday night, cache them. If live regen fails, use the cached spec — the demo still works, we just don't get the "live AI" beat.

### Layer B contract (TouchDesigner, Calin + Bernardo)

- Each generic visual module:
  - **inputs**: subscribes to specific Algoriddim signals exposed by TD's integration
  - **parameters**: named, typed, ranged (e.g. `intensity: 0..1`, `color_hue: 0..360`) — exported into a `parameter-catalog.json` consumed by the AI generator
  - **output**: a render layer that composites with other modules
- Modules are reusable — same module can be wired to different stems or different inputs
- Visual register (abstract vs narrative vs hybrid) is TBD, owned by Bernardo + Calin, converge by Saturday lunch

### Layer C contract (AI-generated controller, Dan + Bernardo)

Three sub-components, all owned by Dan with Bernardo collaborating on UX:

1. **Catalog reader** — pulls the Layer B parameter catalog (JSON exported by Calin's modules)
2. **AI generator** — prompts an LLM (Claude) with `{catalog, scene description, target controller layout}` → returns a `ControllerSpec` JSON: ordered list of controls (knob/toggle/pad/macro), each bound to one or more Layer B parameters with curves and 2–3 high-impact macros per scene
3. **Renderer** — turns `ControllerSpec` into a live web UI (v1) or maps it onto a connected MIDI controller (v2). Writes back to TD via OSC.

**Bernardo collaborates with Dan on the renderer's UX**: widget design (knob/pad/slider visuals), layout aesthetics, scene-swap transition feel. The controller needs to look as designed as the visuals it controls.

**Why this is the differentiator:** swap scenes, regenerate in seconds. Plug a new controller in, regenerate. No team in this hackathon will have that adaptability.

## Risks & mitigations

- **AI output quality / inconsistency** → constrain the LLM with a strict JSON schema, few-shot examples (Guille curates 3–5 hand-designed "good" specs for the prompt), and a validator that rejects malformed specs and re-prompts. Cache approved specs per scene so the live demo can fall back to a cached one if a regen fails.
- **AI latency on stage** → pre-warm the generator with the demo scenes; show a "regenerating..." state that's visually fine for ~3s. Worst case, the scene-swap moment uses a pre-cached spec and we say "AI generated this earlier — here it is."
- **TD-Algoriddim integration coverage gaps** → Friday research task to confirm what's exposed (BPM, stems, deck states, etc.); if a needed signal isn't exposed, the affected Layer B module gets descoped, not the whole pipeline
- **OSC port collisions** between renderer and TD at the venue → hardcode ports, document, test on local network
- **TD performance** with multiple modules → set a frame-rate budget early, plan downgrades (lower res, fewer particles)
- **Layer C complexity creep** → constrain the AI prompt to emit a small, opinionated set of controls (e.g. max 8); the "no thinking" thesis breaks if there are too many knobs
- **Live demo failure** → record full backup demo video Sunday morning; have a scripted segment we *know* works
